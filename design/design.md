# Go SDK design decisions

This document explains the ownership, wire, and API decisions behind
[github.com/Tangerg/acp](https://pkg.go.dev/github.com/Tangerg/acp), a Go
implementation of both halves of the [Agent Client
Protocol](https://agentclientprotocol.com). Use the package reference for API
details and this document for the reasoning behind them.

The wire grammar is not this repository's to design. It is defined by the
published schema. If this implementation disagrees with that schema, the
implementation is wrong. This document addresses the Go representation: message
types, connection ownership, handle lifetimes, and the protocol obligations the
library enforces for applications.

## Prior art and deliberate differences

The initial design compared four existing Go libraries for ACP:

- [`spachava753/acp-sdk`](https://github.com/spachava753/acp-sdk): generated
  types, method constants, handlers and RPC clients, with a conformance suite of
  its own
- [`eino-contrib/acp`](https://github.com/eino-contrib/acp): a bidirectional RPC
  abstraction over three transports: stdio, streamable HTTP and WebSocket, with
  server hosting for Hertz and Gin
- [`ironpark/go-acp`](https://github.com/ironpark/go-acp): connection options and
  middleware, a session stream abstraction, and helpers for spawning an agent and
  matching session updates
- [`coder/acp-go-sdk`](https://github.com/coder/acp-go-sdk): a close port of the
  reference TypeScript SDK

This package diverges in three load-bearing areas:

- **Three-state optional properties**: the protocol
  distinguishes absent from explicit null in places where the difference is
  load-bearing, and a `*T` collapses them at the boundary rather than at the
  point where a decision is made.
- **Library-owned protocol obligations**: a cancelled turn must
  still be answered with the cancelled stop reason; a client that cancels must
  answer the permission requests it left outstanding; a session that is closed
  must have its work cancelled first. An application that has to remember these
  will eventually not.
- **Published schema inputs**: types are generated
  from a vendored release asset and committed, so that a schema change is a
  reviewable source diff.

The last of those is the one that separates this package from all four rather
than from some of them, and it was re-checked against them rather than assumed.
Upstream publishes two schemas per release: `schema.json`, the stable grammar, and
`schema.unstable.json`, which is that plus whatever is being tried. The original
comparison used `schema-v1.21.0`: its unstable asset added 95 definitions and 17
methods, including `session/fork`, `nes/*`, `providers/*`, `document/did*` and
`mcp/connect`. That comparison records the initial design evidence; the current
stable input is selected by `schema/provenance.json`.

All four generate from the unstable channel. `spachava753/acp-sdk` and
`eino-contrib/acp` generate from it alone, so their entire public API is the
moving one; `eino-contrib/acp` reads it from an unpinned `main` URL, so two builds
a week apart need not agree. `coder/acp-go-sdk` merges the two into one type set,
and `ironpark/go-acp` keeps them in separate files inside one package, each
experimental type carrying an `**UNSTABLE**` doc line and nothing a compiler
checks.

This package generates from the stable release asset alone, pinned by tag and
SHA-256. What that buys is the thing every other guarantee here rests on: an
exported surface that is a published grammar, so `gorelease` comparing this
module against its last tag is comparing something upstream also promised not to
move. What it costs is stated below.

Two things were taken from other libraries deliberately. The `Transport` and
`Connection` abstraction is the one the [official MCP Go
SDK](https://github.com/modelcontextprotocol/go-sdk) arrived at, and the argument
for it there applies here unchanged. The bound on queued messages is
`coder/acp-go-sdk`'s idea; what a connection will hold is discussed below.

## Design goals

- **Complete**: every method the specification defines is classified, and all 25
  are served. The classification for one that is not survives, because a method
  arriving in a schema bump has to be answerable before it is implementable
- **Faithful**: types come from a published schema release, the
  generator refuses anything it cannot represent exactly, and the corpus of
  fixtures is generated by the reference implementation's own deserialisation
  machinery
- **Idiomatic**: handlers take `(ctx, *Params)` and return `(*Result, error)`.
  Configuration is a struct. Cancellation is a `context.Context`. Nothing is
  invented where the standard library or an established Go idiom already answers
  the question
- **Obligation-keeping**: when the protocol requires work that an application
  could omit, the connection owns that work and tests its lifecycle
- **Robust**: `testing/synctest` and the race detector cover concurrency and
  shutdown on three platforms. Independent fixtures and transcripts cover the
  wire
- **Evolvable**: a pinned schema, a checked capability table, and an extension
  API for `_`-prefixed methods allow protocol growth without silently widening
  the stable grammar

## Wire and package foundations

### Package layout

Almost all of the API lives in one package, `acp`, following `net/http`,
`net/rpc`, and the MCP Go SDK. Splitting `client` and `server` would create an
import boundary inside a protocol whose two halves call each other.

```text
github.com/Tangerg/acp                         the API: both peers, sessions, turns, the generated types
github.com/Tangerg/acp/jsonrpc                 the JSON-RPC envelope: messages, identifiers, decode errors
github.com/Tangerg/acp/internal/wire           the codec runtime the generated types are written against
github.com/Tangerg/acp/internal/jsonnumber     exact JSON integers, without float rounding
github.com/Tangerg/acp/internal/cmd/schemagen  the generator
```

`jsonrpc` is public because a custom transport has to name the message type it
carries, and nothing else about JSON-RPC is a caller's business: request
lifecycle, cancellation and shutdown are the connection's. It defines the
envelope types itself rather than aliasing an internal package, because an alias
shows no fields or methods in the documentation a transport author reads. The
envelope descends from `x/tools/internal/jsonrpc2_v2`, narrowed where ACP
narrows JSON-RPC: identifiers keep explicit null apart from absence and accept
only `int64` numbers, and an error object is carried as validated JSON whose
grammar the generated `Error` owns.

### Generate and commit protocol types

`schema/schema.json` is the published stable release asset selected by
`schema/provenance.json`. That file also owns the schema and metadata hashes,
the reference TypeScript commit, and shared tool pins. The generator and both
recording scripts read that source directly. `schema.gen.go` is generated from
the vendored schema and committed.

Committing the output is the decision worth arguing about. It means `go get`
needs no generator and no network, `pkg.go.dev` has something to document, and a
schema change arrives as a source diff a reviewer can read. The cost is that the
output can drift from its input, which is why `schemagen -check` runs in CI: it
regenerates and fails if anything differs. This also proves deterministic output;
Go map iteration cannot determine generated source order.

What gets generated is the transitive `$ref` closure of a committed root set
(`schema/manifest.json`). A root is added when an operation needs it, so the exported surface is an output CI
checks rather than a number maintained by hand. The generator refuses rather than
guesses: a union it cannot discriminate, a numeric bound the Go type does not
already enforce, or an inline object type stops generation with the definition
named.

JSON-RPC envelopes are deliberately not generated. Package `jsonrpc` owns
JSON-RPC's grammar, and a second set of types for it would be two sources of
truth for the one part of the wire the protocol did not invent. Where a payload
names a request — the schema's `RequestId` — the manifest binds the definition to
`jsonrpc.ID` instead of generating a second identifier type, and generation stops
if a release changes that definition's shape.

### Three JSON states

The protocol distinguishes three states for an optional property: absent,
explicit `null`, and a value. The API preserves all three:

```go
type Opt[T any] struct{ /* absent | null | value */ }

func OptValue[T any](v T) Opt[T]
func OptNull[T any]() Opt[T]
func (o Opt[T]) Get() (T, bool)
func (o Opt[T]) IsNull() bool
```

Other reviewed Go libraries model optional properties as
`*T`. A pointer has two states, so an implementation using one must decide at the
codec boundary whether a missing property and a null property are the same thing
for every property. `Opt` leaves that decision to domain code with the context to
make it. The caller pays one `Get` operation to retain a wire distinction that a
pointer would erase.

`_meta` is the protocol's reserved extension object, and it is a closed value
type rather than a `map[string]any`:

```go
func NewMeta(values map[string]any) (Meta, error)
func (m *Meta) Set(key string, value any) error
func (m Meta) Decode(key string, target any) (bool, error)
```

It stores encoded JSON. What the protocol promises is unknown JSON, not Go object
identity, and holding the encoded form is what makes a `Meta` copyable: a
configuration and a `Negotiated` snapshot are both handed out as copies, and an
arbitrary Go object with hidden mutable state inside one would make both a lie. It
also means a value that cannot cross JSON fails at `Set`, naming the key, rather
than at some later protocol write that cannot say what went wrong.

### Define transport ownership

A transport is a bidirectional message stream and nothing more:

```go
type Transport interface {
	Connect(ctx context.Context) (Connection, error)
}

type Connection interface {
	Read(ctx context.Context) (jsonrpc.Message, error)
	Write(ctx context.Context, message jsonrpc.Message) error
	Close() error
}
```

This is the MCP Go SDK's abstraction, adopted because the argument for it holds
here: a higher-level transport with methods for calls and notifications is harder
to implement and pushes protocol concerns into something that should only move
bytes. Four implementations ship, each constructor returning its concrete type:

| Transport | Role |
| --- | --- |
| `CommandTransport` | spawns an agent and owns its pipes for a client |
| `StdioTransport` | uses an agent's own stdin and stdout |
| `InMemoryTransport` | two peers in one process; what this package's tests run over |
| `IOTransport` | byte streams with one explicit release owner in `IOConfig` |

`Close` unblocks both reads and writes. A write honours its context only while it
waits for the stream, where giving up commits nothing and the exact context error
says so. From the first byte it finishes or fails, because cancellation cannot
prove which prefix reached the peer. That is what keeps one caller's cancelled
context — a turn the user stopped while its update was half written — from
ending a connection every other session shares. `IOConfig.Close` must unblock
I/O on both configured streams. A short write is a failure, never a message.

A line framing delivered intact but JSON-RPC cannot decode is a
`*jsonrpc.DecodeError`, not a broken stream. The connection answers it with
parse-error or invalid-request, or fails the one call a malformed response
names, and keeps reading. Ending the connection over one bad line would hand any
peer a way to take down every session on it.

A process's standard streams are not the connection's to close, and closing an
inherited blocking descriptor would not interrupt a read anyway. `StdioTransport`
therefore runs each blocking read and write on a goroutine that `Close` abandons,
so `Agent.Run` returns when its context ends even while the client holds stdin
open.

The reader and writer are I/O views; only the configured close callback owns
release. The connection invokes it once, including when cancellation and explicit
close race, and shares its error with every closer. This avoids closing a shared
read/write resource twice. Separate pipes use a callback that closes both and
joins their errors. Failed connection setup leaves ownership with the caller.

An outbound operation returns its own write error. Closing the stream may wake
the reader first, so the connection's first terminal error can differ; that error
belongs to `Wait` and cannot replace the operation's deadline or write failure.

Shutdown of a spawned agent is bounded rather than best-effort: closing the
connection closes the pipes, waits, asks the process to stop, waits again, and
finally kills it, with `CommandConfig.TerminationGrace` as each step's deadline.
Before start, a zero `exec.Cmd.WaitDelay` takes the effective grace period; an
explicit value stays unchanged. Process exit and output-copy completion are
different facts: inherited diagnostic pipes may keep the copy running after the
agent is gone. `WaitDelay` bounds those pipes, while a caller-supplied writer must
finish its own `Write` calls.

The agent's exit status is not the connection's error. An agent that exits
non-zero after a shutdown request has still stopped. Expected exit status and
bounded pipe drainage are ignored; unexpected copy errors and failure to reap
remain connection errors. `transport_command.go` owns this process lifecycle,
and `transport_io.go` owns byte framing and stream release for every byte-stream
transport.

`NewInMemoryTransports` carries messages rather than bytes. An in-memory
transport that encoded and re-decoded would be testing the codec twice and hiding
framing bugs rather than exposing them; framing is the byte-stream transports'
business, and they are tested for it separately.

## The two peers

```go
func NewClient(config *ClientConfig) (*Client, error)
func NewAgent(config *AgentConfig) (*Agent, error)

func (c *Client) Connect(ctx context.Context, t Transport) (*ClientConn, error)
func (a *Agent) Connect(ctx context.Context, t Transport) (*AgentConn, error)
func (a *Agent) Run(ctx context.Context, t Transport) error
```

A `Client` or `Agent` holds the handlers and the advertisement and may open many
connections. A `ClientConn` is one logical link. A `ClientSession` is one
conversation on it, and a connection carries many.

The naming follows the specification. `session/new` returns a session identifier,
and a session has its own history. Calling the connection a session would put
`NewSession` on a type named `ClientSession`.

### Handlers are struct fields, not interface methods

```go
type ClientConfig struct {
	SessionUpdate     func(ctx context.Context, conn *ClientConn, notification *SessionNotification)
	RequestPermission func(ctx context.Context, conn *ClientConn, request *RequestPermissionRequest) (*RequestPermissionResponse, error)
	ReadTextFile      func(ctx context.Context, conn *ClientConn, request *ReadTextFileRequest) (*ReadTextFileResponse, error)
	WriteTextFile     func(ctx context.Context, conn *ClientConn, request *WriteTextFileRequest) (*WriteTextFileResponse, error)
	Terminal          *TerminalHandlers
	// Optional handlers omitted.
}
```

The reference implementation declares an interface with fourteen methods, twelve
of them optional. Go has no optional interface methods, so transliterating that
would make every caller write ten stubs and would leave capability advertisement
as a second list to maintain by hand.

Fields solve both problems because setting a handler advertises its capability.
There is no way to advertise `fs.readTextFile` and
not implement it, and no way to implement it and forget to advertise it.

The unit is the capability group rather than the method, because the
specification's capabilities are not one-to-one with methods: `fs` is two
independent booleans, so it is two independent handler fields; `terminal` is one
boolean documented as covering all five `terminal/*` methods, so it is one
`*TerminalHandlers` struct whose five fields are all-or-none, checked at
construction.

`Capabilities` may be stated explicitly as a complete advertisement. A
field-by-field merge would need to distinguish "set to false" from "not set",
but a boolean has no third state for that distinction. Advertising more than the
handlers can serve fails at construction rather than on the first call.

Several reviewed Go libraries offer functional options
(`WithMiddleware`, `WithLogger`). This package uses explicit `Config` structs
throughout. An option function is a closure whose effect is discoverable only by
reading its implementation; a struct field is visible in the type, in the
documentation and in an IDE, and it composes with the language's zero values.

### A handler is given the handle its method is scoped to

`Prompt`, `Cancel`, and every other handler whose published params require
`sessionId` take an `*AgentSession`. The connection-scoped handlers once took
nothing, which meant a handler with no session could make no outbound call at all
— and the case the schema describes for a request-scoped elicitation is exactly
one of those: an agent asking for something from inside its own `authenticate`
handler, before a session exists.

`NewSession`, `Authenticate`, `Logout`, and `ListSessions` therefore take an
`*AgentConn`. Whether a method's params require `sessionId` is read from the
schema's routing unions into the generated method table, and a session binding
accepts only a request type that names its session, so the handle a handler is
given is a compile-time fact rather than a convention. It also makes
request-scoped elicitation reachable where the specification puts it rather than
only from handlers that happen to hold a session.

`Cancel` is optional. The connection cancels the running `Prompt` handler's
context when `session/cancel` arrives, so the obligation is kept whether or not
the application observes the notification.

`NewSession` chooses the session's identifier, so it cannot be given the session
it is creating, and the client cannot route an update naming that identifier
until the answer reaches it. `SessionOpened` is the moment both hold: it runs
after the answer to `session/new`, `session/load` or `session/resume` is written.
Before it, an agent had no handle at all for a new session until the client's
first prompt, so Zed showed a new thread without its slash commands. A handle
obtainable from the connection by identifier was the alternative; it would let
an agent update a session before the client knew it, which is the ordering this
hook exists to guarantee.

Every client handler receives `*ClientConn` after its context. A shared client
can drive several agents, and two agents may use the same session identifier.
Holding all connection handles does not tell a callback which one produced its
payload. The explicit connection supplies that scope without changing the wire
message. The setup context is not a hidden channel for connection identity.

Extension fallbacks receive the originating `*ClientConn` or `*AgentConn` too.
Their payload remains undecoded because its grammar belongs to the two peers;
its connection identity belongs to this SDK regardless of that grammar.

### Capabilities are an authority boundary

Capabilities are not a feature list. They decide whether an agent may read a
file, write one, or run a command on the user's machine, and this package
enforces them in both directions:

- **Outbound**: a call the peer never advertised is refused before it is sent.
  The answer would be the same after a round trip, and refusing locally means a
  developer reads an error naming the capability instead of a wire trace. The
  refusal wraps `ErrNotAdvertised` rather than carrying a wire code, because a
  caller deciding what to do next needs to know that the peer never saw it.
- **Inbound**: a request for a method this side never advertised is refused
  before it reaches a handler. The peer was told it was not there, and a
  capability that is only advertised is not a boundary.

The table that maps method to gating capability is written once, because the
schema links a method to its capability only in prose. Each row is one
descriptor that both reads and writes its leaf, so the gate and the
advertisement derived from the handlers cannot name different capabilities, and
the table is checked against the generated method list in both directions, so a
method added by a schema update cannot quietly arrive ungated.

Other capabilities gate what a payload carries rather than the method. A client
may send only prompt content the agent's `promptCapabilities` admit, an `http`
or `sse` MCP server only with the matching `mcpCapabilities`, and
`additionalDirectories` or a system prompt only to an agent that advertised
them. An agent may send notice, compaction, plan and subagent updates only to a
client that advertised them. A boolean session configuration option is granted
through the client's advertisement for both sides, which makes it the one
capability a side reads about itself. Each rule is a method on the payload type
it constrains, and every standard payload leaves through one boundary that calls
it, so a rule is stated once and cannot be skipped by a path that forgot it.
When a peer sends such a value anyway, the answer is invalid-params rather than
method-not-found: the method is available, and it is what the sender put inside
it that was never advertised.

Every capability is read by something. A test walks the capability tree the
schema defines and holds each leaf against what reads it, so a capability added
upstream cannot arrive as a grant this package accepts and never acts on.

They are deliberately not enforced inbound, and the difference is what a
capability means in each case. A method capability is authority — whether an
agent may read a file or run a command — so it is enforced at both ends and a
peer that ignores it is refused at the door. A parameter capability is
comprehension: an agent that did not advertise images is saying it cannot read
one, not that it forbids being sent one. Refusing it inbound would make an agent
built on this package reject work it could actually do.

### Handshake ownership and ordering

`Client.Connect` returns a connection that is already initialized: the transport
connected, `initialize` was answered, the negotiated version is one this package
implements, and the peer's capabilities are stored. If any of that fails, the
connection is closed before returning.

There is no exported `Initialize`. Such a method would require contracts for a
call before initialization, a second initialization, and concurrent
initializations. Keeping the operation inside `Connect` makes those client-side
states unrepresentable.

The agent side cannot be symmetric, because it answers a handshake rather than
performing one. `Agent.Connect` returns once the read loop is running; until
`initialize` arrives, every other method is answered `-32600`. Two consequences
are worth stating:

- **Nothing this side sends can precede the initialize response.** The
  agreement is negotiated when the request is read and opened for this side's
  own sends only once the answer has been written, so an agent's own outbound
  call cannot overtake the
  response that told the client what was agreed. A boolean flag set after the
  write is inherently late: the client observes the answer *during* the write,
  and the request it sends next is served on a different goroutine.
- **Initialize is judged in wire order.** It is negotiated when it is read rather
  than when a goroutine gets to it, so a request that follows it on the wire is
  served under the agreement it settled, and one that precedes it is refused.
  A later initialize renegotiates, as the reference implementation allows; the
  schema does not forbid it, and refusing it would be a local dialect.

The agreement is a `Negotiated` value, stored once and never mutated. The gate
reads the stored value directly; `ClientConn.Negotiated` and
`AgentConn.Negotiated` hand callers a deep copy.

The connection's completed lifetime removes it from its client's or agent's
registry, including when completion races registration. `Conns` enumerates live
membership; observing it does not cause resource cleanup.

A protocol version is a grammar, not a feature level. This package speaks version
1, so it answers 1 and refuses any other answer, rather than taking the minimum
of two numbers and claiming a grammar it does not have.

## Sessions and turns

```go
func (c *ClientConn) NewSession(ctx context.Context, params *NewSessionRequest) (*ClientSession, *NewSessionResponse, error)
func (s *ClientSession) Prompt(ctx context.Context, params *PromptParams) (*PromptResponse, error)
func (s *ClientSession) Cancel(ctx context.Context, params *CancelParams) error
```

A handle binds the session identifier to its connection and holds nothing else.
Twenty definitions in the schema carry a `sessionId`, and threading that string
by hand through every operation that needs it invites mismatched identifiers. A
terminal handle solves the same problem for the five terminal calls.

Whether a session exists is the application's fact, so the connection keeps no
cache of handles that could disagree with it. Two handles for one session are
interchangeable values; the per-session state the protocol does require — the
active turn — is indexed by identifier and lives only while a turn does.

Handles are connection-bound. A `SessionID` outlives the connection it came from;
a handle does not, so loading the same identifier on a new connection returns a
handle bound to that one. One that silently re-pointed at another transport would
be a lifetime nobody could reason about.

`ClientSession` and `AgentSession` are different types with different methods,
because a client never calls `RequestPermission` and an agent never calls
`Prompt`. One type carrying both method sets would make those calls compile and
fail at runtime, which is a worse place to find out.

Operations return both the response and the handle when the response contains
more than an identifier. For example, `session/new` also returns modes,
configuration options, and `_meta`.

A close or delete answered resource-not-found leaves the same end state as a
successful one, so it is reported as success, as the reference implementation
does.

A request's session is decoded once, by the generated codec, when the request is
read. The turn rule, cancellation and the handler's handle all use that one
reading; a second, more lenient decoder would let a message with two spellings of
`sessionId` claim one session's turn and cancel another's. A handler that edits
its request cannot redirect the turn's completion either.

### One prompt at a time

A second overlapping prompt on one session returns `ErrPromptInProgress`.

This is not a scheduling choice. `session/cancel` carries a session identifier
without a turn or request identifier. Two active turns would make the target of
cancellation ambiguous. Enforcing one active turn also lets the connection index
pending permission requests by session.

A session is safe for concurrent use. That is a different question from whether
two prompts may overlap, and the answer to the first is yes while the answer to
the second is no.

Each active turn has its own record. Delayed completion and permission cleanup
retain that record rather than looking up a possibly newer turn by session ID.
Completed turns leave the connection's index after their cancellation writes
finish; no historical generation counter remains for every session ever seen.
The prompt sender alone closes the turn's send-completion channel. Cancellation
waits for that boundary before sending its notification, so a locally registered
turn cannot be cancelled on the wire before its prompt arrives. A prompt started
while a cancellation of the same session is still being written waits for it
rather than being refused.

`ClientSession.Cancel` is committed once it starts: its context decides only
whether it starts. Answering the pending permission requests cancelled cannot be
undone, so stopping halfway would leave a turn this side considers cancelled and
an agent that was never told. The remaining waits and the notification run under
the connection's own bounded deadline, and a failure to write the notification
ends the connection, because the two peers would otherwise disagree about the
turn.

### Two cancellations, which are not the same thing

`$/cancel_request` cancels one JSON-RPC request. `session/cancel` cancels a turn,
and obliges the agent to finish the outstanding `session/prompt` with the
cancelled stop reason. Cancelling a `Prompt`'s context does the first;
`ClientSession.Cancel` does the second.

Separating them leaves obligations that cannot be an application's problem, and
the connection takes them:

- A client that cancels a turn must answer every pending
  `session/request_permission` for that session with the cancelled outcome. This
  includes a handler blocked on a dialog and a request that arrives while
  cancellation is still running. The connection claims those requests before
  sending the notification. A later user decision then finds the request already
  answered and is discarded. Concurrent cancellations retain the same pending
  response obligations until settlement, so one cannot overtake another's writes.
- An agent whose turn is cancelled must still answer the prompt. The handler is
  free to return its context error, as model and tool libraries commonly do. The
  connection turns a committed cancellation into `StopReasonCancelled` rather
  than letting an abort error leak as `-32603`, which the specification
  explicitly warns against, and keeps the `_meta` of a response the handler did
  return.
- A client must keep accepting `session/update` after it has cancelled, because
  the agent may have final tool-call updates to report before it answers. This is
  a rule for the application, not something the library can enforce, so it is
  documented on `Cancel` and demonstrated in a runnable example. The agent sends
  those updates with a context that outlives the cancelled turn.
- A permission request whose answer cancellation already claimed is not handed
  to its handler, so the user is never shown a question nobody can answer.

### Ordered delivery, and the one rule it imposes

Inbound messages pass through an ordered stage before dispatch. Two promises
depend on it:

- `session/update` is an ordered stream of chunks, tool calls, and plans. Serving
  two notifications concurrently would scramble a turn's output.
- A response is delivered only after every notification that preceded it on the
  wire. A cancelled turn depends on exactly this: the permission outcomes the
  client owed the turn are delivered before the cancellation that chased them.

The rule this imposes on callers is short and unavoidable: **a notification
handler must not make a call on the same connection and wait for it**, because
the response it waits for is queued behind the handler that is waiting. Spawning
the work is the answer, and a session handle stays valid beyond the handler call
for exactly that reason.

### How a connection is put together

One `link` coordinates four collaborators. Each collaborator owns one invariant;
combining them behind unrelated mutexes would hide the ordering relationships:

| Collaborator | Responsibility |
| --- | --- |
| `lifetime` | transport release, reader exit, delivery completion, and the terminal error |
| `queue` | the ordered stage: nothing is dispatched before the messages that preceded it |
| `calls` | the outbound half: requests sent and not yet answered |
| `requests` | each inbound request's identity, response claim, settlement, and retained handler work |

Above the link sits one dispatcher per client or agent, generic over the
connection type, and a connection's link side is that dispatcher bound to it. Its
rows are built from the configuration at construction, one per method that has a
handler, so the derived advertisement and inbound dispatch read the same set: a
method is advertised and served exactly when it has a row. Both peers judge every
inbound message by the same steps, once and in wire order: initialize first, then
whether the name is the specification's or reserved for extensions, its shape,
whether this peer is the one that serves it, the capability gate, and its params,
decoded once. Every request row is built by one constructor, which is also what
holds a handler to returning a response or an error. The link itself knows
JSON-RPC and nothing of the protocol's method table.

Only the reader can signal that no more messages will enter the queue. Closing
the transport may race a successful read whose response has not yet been queued.
Delivery ends after reader exit and queue drainage, so a waiting caller receives
that response before observing connection closure. Notifications started during
drainage use an uncancelled context regardless of their batch. Requests retain
their own cancellation, and notification handlers already running at shutdown
receive the connection's cancellation as before.

The request record owns the right to answer. Turn cancellation and the returning
handler ask that same owner to claim it; only one succeeds. Automatic refusals
use this path too. The claim removes the record from the unanswered map before
writing, because the peer may receive the response and reuse its ID before the
write returns. Response delivery and handler work retain the original record and
count against the in-flight bound until both finish. Old work cannot answer or
remove a newer request that reuses the ID.

The response writer makes the final error decision after attempting result
encoding. For a request cancelled through `$/cancel_request`, both handler and
encoding failures become `-32800`; a valid completed result may still be sent.

A request-scoped elicitation holds its parent's send gate during the write. The
response claim closes admission through the unanswered map, then waits for any
admitted write before answering. This wait and the response write share one
deadline, so a peer that stops reading cannot hold the parent indefinitely.
Waiting for the elicitation's response does not hold the gate.

Response delivery updates connection-owned state and hands the response to its
waiter. The waiter decodes caller-owned result objects, so a custom decoder can
make another call and cannot keep modifying a result after its call returns.

## Workspace access

An agent reaches the user's machine through the client, and every operation is
gated on a capability the client advertised.

```go
func (s *AgentSession) ReadTextFile(ctx context.Context, params *ReadTextFileParams) (*ReadTextFileResponse, error)
func (s *AgentSession) WriteTextFile(ctx context.Context, params *WriteTextFileParams) (*WriteTextFileResponse, error)
func (s *AgentSession) CreateTerminal(ctx context.Context, params *CreateTerminalParams) (*TerminalHandle, *CreateTerminalResponse, error)
```

Every path the protocol carries must be absolute, so this package never sends one
that is not — here, and on the `cwd` and `additionalDirectories` a client sends
with a session. The check is deliberately not `filepath.IsAbs`: that answers for
the operating system this process is running on, and the path describes the
peer's filesystem. Nothing requires two peers to share one, so a path absolute
under either convention is accepted, which still refuses what the rule exists to
refuse — a path whose meaning depends on a working directory the two peers do not
share.

The refusal is on the way out only. The specification puts the obligation on
whoever writes the path, and a receiver refusing a relative path is a policy an
application may reasonably want to set for itself; `SECURITY.md` already names a
path arriving from a peer as a boundary the application owns. The example client
uses an open `os.Root` for the actual file operations, so containment also holds
during symlink resolution instead of ending at a lexical path check.

A `TerminalHandle` binds the session and terminal identifiers required by all
five terminal methods. It is named `TerminalHandle` rather than `Terminal`
because the schema already defines `Terminal` as the payload of a tool call's
terminal content, and the schema's names are not this package's to reassign.

Release is one-way and enforced by the type. Once a release reaches the
transport, every operation on the handle, including a second release,
returns `ErrTerminalReleased`. A released identifier is the client's to reuse, so
an operation on a stale handle is not merely pointless: it may name a terminal
that now belongs to something else, and the client would serve it. A refusal
before the request reaches the transport rolls the claim back, so a caller can
correct a context and retry.

Terminal creation is a resource acquisition transaction. Cancelling its waiter
does not discard a response that may still transfer a live terminal. One response
observer either delivers the handle or schedules a release with a separate,
bounded cleanup budget. Cleanup never blocks ordered delivery. Its failures are
logged; uncertain write commitment is not retried, and unrelated sessions are not
closed to hide the failure. Retained response observers count against
`Limits.PendingCalls` until the response or connection shutdown settles them.

The handle serializes admission and sending with release, preventing an earlier
operation from being sent after release. It unlocks before waiting for responses,
so a pending `WaitForExit` does not prevent `Kill` or `Release`. Handle copies
share one state record; copying a value cannot create a second release right.

## Safe extension methods

Both peers can send and receive methods the specification does not define, and
this package exposes exactly that:

```go
func (c *ClientConn) Call(ctx context.Context, method string, params, result any) error
func (c *ClientConn) Notify(ctx context.Context, method string, params any) error
```

The method must begin with an underscore, which is the protocol's reservation,
and a name the specification defines is refused. An unrestricted method string
would be a hole through every invariant here: a caller could pass `session/prompt`
and bypass the generated params type, the outbound gate, the session binding and
the capability check. A standard method has exactly one path through the typed
codec, and this keeps it the only one.

Inbound extension messages reach `CallFallback` and `NotifyFallback` with their
originating connection and undecoded payload. What that payload carries is
between the two implementations that agreed on it.

## Resource limits

By default, a connection holds at most 1024 messages read but not yet delivered,
1024 inbound calls, 1024 outbound calls waiting for responses, and 1024 URL
elicitations awaiting completion. Every breach reports `ErrLimitExceeded`,
wrapping which bound it was. Sessions are not counted, because the connection
holds no state per session beyond an active turn.

Breaching the delivery or request bound ends the connection. Refusing to read
until the backlog drains would turn the documented rule that a notification
handler must not wait on its own connection into a deadlock, because the
response that would release it arrives on the read loop that is no longer
reading. The pending-call limit refuses new work before writing it, without
closing the connection. Observed calls retain their slot after a waiter cancels
because their late answer may still own a resource or protocol state.

The URL bound is different again, because the protocol makes
`elicitation/complete` optional: an honest agent may never send it. Refusing new
elicitations once the bound filled would let a long session break itself, so the
oldest accepted interaction is forgotten instead, which costs only the duplicate
check for an identifier that old.

These counts bound how much state a peer can create. They are not memory proofs
because one legal message can still be large.

The four are `Limits` on both configurations, with a zero field taking the
default and a negative one refused at construction. The delivery backlog is the
one an honest connection most readily reaches: a turn's `session/update` stream
is produced by an agent and consumed by a handler that may render it, so its depth
is a fact about the application rather than the protocol. A constant chosen here
would decide on every caller's behalf how slow that handler may be before the user
loses a session. The package cannot know that, and the field is where a caller who
does says so.

## Error model and privacy

```go
type Error struct {
	Code    ErrorCode
	Message string
	Data    Opt[json.RawMessage]
}
```

`Error.Is` matches on the code rather than on identity, because that is the
question a caller actually asks: "did the agent say I must authenticate first?"
is about a code, and answering it should not require extracting a value and
comparing a field.

Sentinels exist only where control flow needs one. `ErrAuthRequired` is the
important one: an agent answering `session/new` with `-32000` is a documented step
in the lifecycle rather than a failure, and `errors.Is` is how a client tells them
apart. `ErrResourceNotFound` is the other code the protocol gives a meaning a
caller branches on: closing or deleting a session that is already gone succeeds,
and a missing file is how a client says a path is free. `ErrorCode` constants plus
`errors.As` already cover ordinary inspection, and a sentinel per code would be API
surface nobody asked for.

The local sentinels answer the one question an `*Error` cannot: did the peer say
this, or did it never see the request? `ErrNotAdvertised` is a local capability
refusal, `ErrLimitExceeded` a local bound, and `ErrConnectionClosed` an operation
on a connection that has ended, wrapping the failure that ended it when there was
one. `Close` reports only what closing itself did; why the connection ended is
`Wait`'s to report, so a deferred `Close` never returns somebody else's error.

A handler's error is not relayed unless it is deliberately an ACP `Error`.
Arbitrary Go errors routinely contain paths and host identifiers; the peer gets
`-32603` and the detail goes to the configured logger. `nil` for a logger means
discard. The package never chooses a default logger because an agent's stdout is
the protocol stream; writing diagnostics there would corrupt the connection.

## Elicitation

Elicitation is the agent asking the user for structured input through the client
that owns the user, and it is one feature rather than two methods.
`elicitation/create` carries a mode and a scope, both unions the schema flattens
into the same JSON object. Form mode hands the client a JSON Schema to render.
URL mode gives the client a URL. An `accept` response is the user's consent to
start that out-of-band interaction; it is not a completion. The agent may later
send `elicitation/complete` when the accepted interaction has finished.

### The mode is the caller's and the scope is the operation's

This is the division every handle in this package already makes. A
`ClientSession` never spells a session identifier and a `TerminalHandle` never
spells a terminal identifier, and here an agent never spells a scope, because the
operation it called has decided one. `AgentSession.CreateElicitation` elicits
within its session. `AgentConn.CreateElicitation` elicits within the request being
served, which is what the schema means by a request-scoped elicitation: the phases
before any session exists.

An agent never spells a request-scoped elicitation's `RequestId`: the
connection fills the scope in from the context the request travels on. A client
receives it as `ElicitationRequestScope.RequestID`, a `jsonrpc.ID`, because the
schema puts it on the wire for the client to correlate with the request it
answers, and a client cannot match what it cannot read.

The context retains the original inbound request record. The operation checks
that the record belongs to this connection. The unanswered map owns both send
admission and the response claim; copying a context or reusing a wire ID cannot
give another request that scope. The send gate orders admitted writes before the
response.

The mode is deep-copied before the scope is written into it. The value is the
caller's, and an agent holding one prepared schema and eliciting with it twice
would otherwise find the second call carrying the first call's scope.

The client compiles a private form before invoking a handler, and an agent
compiles its form before sending it. Malformed schemas fail at those boundaries,
even when the eventual answer would be a decline. Answer validation reuses that
compiled object; edits to the handler's wire model cannot change the constraints.

### Two modes, two capabilities, one method

`elicitation` says the client serves the method; `elicitation.form` and
`elicitation.url` say which shapes it can render. So `ElicitationHandlers` is two
handler fields that advertise themselves, the way the two file-system booleans
are two fields, and the dispatcher routes on the mode the request carries.

A mode with no handler is refused with invalid-params rather than
method-not-found, which is the rule the other parameter capabilities follow: the
method is there and this client advertised it, and it is what the agent put inside
it that was never advertised. Telling an agent the method does not exist would be
false and would send it looking in the wrong place.

`elicitation/complete` is the exception that gates a method on a mode. It exists
only to finish a URL elicitation, so `elicitation.url` gates the method itself.

Construction refuses two shapes that cannot do what they claim. A group serving
neither mode advertises nothing, and a completion handler without a URL handler
can never run. The inverse is valid: the protocol makes the completion optional,
so a URL handler does not require a completion handler.

### A URL identifier is a transaction

The identifier is reserved before create work starts, so concurrent requests
cannot reuse it. The response commits that reservation only for the known
`accept` action; decline, cancellation, a custom future action, and failure roll
it back. Once accepted, the ID remains unique until a completion is successfully
written or the bound described under resource limits forgets it.

Completion has its own in-flight state. Removing the ID before the write would
make a context deadline lose an interaction even when the transport proved it
committed no bytes; leaving it generally reusable would let two concurrent
completions race. The state machine therefore moves accepted → completing,
commits deletion after a successful write, and rolls back only for the transport's
exact no-commit signal. Each state record has identity in addition to its wire ID,
so a delayed rollback cannot alter a newer reuse of that ID.

The create response is also observed after its original caller stops waiting.
Once the request may be on the wire, that late response alone decides whether the
connection owns an outstanding interaction. This is the same lifetime distinction
as a prompt: cancelling one waiter does not erase protocol state already shared
with the peer.

The recorded Zed transcript advertises both modes, so the gap this used to be
affected an observed client. That the gap is closed is now asserted against the
editor's own recorded advertisement rather than against a capability object
written to agree with the answer.

### What implementing it found

The schema's `ElicitationSchema.properties` is a map whose values are a union, and
it is the first one in the closure. A map of unions was going to `encoding/json`,
which cannot write a discriminant that belongs to the union rather than to the arm
and cannot decode into an interface at all. This package encoded `{"branch":{}}`
for a value that had to read `{"branch":{"type":"string"}}` — a message it could
not read back, put on the wire without an error.

Nothing had caught it because no generated type had such a map. The codec property
could not reach it either: a zero value's map is nil. `wire` now has
`MarshalMapFunc` and `UnmarshalMapFunc` beside the slice pair, and the generator
emits them when a map's values are a union.

Form field types, required fields, bounds and declared formats use
`github.com/santhosh-tekuri/jsonschema/v6`. Both schema bounds and answer numbers
retain their exact JSON representation, including adjacent integers beyond
float precision. The generator uses the same validator for schema structure,
references, and defaults. External schema loading is disabled in both paths.

The form adapter compiles a private projection: a catch-all arm is not partially
interpreted, and optional nulls become omissions as ACP requires. Counts larger
than Go can represent become equivalent constraints: a larger maximum cannot
exclude any string or slice, and a larger minimum cannot admit one. Metadata and
the source wire model remain unchanged. Declared formats are assertions in this
adapter, including email, URI, date and date-time. Pattern syntax and matching
belong to the pure Go engine `github.com/faustbrian/go-ecma-regexp/v2`, using its
JSON Schema profile with Unicode semantics and unanchored search. Parsing,
compilation and execution have explicit budgets. The pattern owner checks
matches separately from the JSON Schema library's boolean adapter so that
resource-limit and cancellation errors remain errors rather than ordinary
mismatches. Neither invalid patterns nor exhausted limits are ignored.

The URL field itself follows the published `format: "uri"` grammar. That is not
the same language as the TypeScript reference's WHATWG-style URL helper: values
such as `mailto:`, `urn:`, and `https:` are absolute URIs even where that helper
would reject them. This package deliberately follows the schema, keeps the URI
error at the generated `/url` property path, and records the divergence in a unit
test rather than changing the wire grammar to match one implementation.

Writing the fixtures found the second one, and it is the same shape of mistake:
the generator was reading a catch-all arm's declared properties and silently
ignoring the arm's own `anyOf`. Each elicitation mode carries a scope union, and
the catch-all carries it too — a custom mode still has to say whether it belongs
to a session or to a request. Without that, this package accepted a message the
published schema rejects and the reference implementation refuses, and handed an
application an elicitation belonging to nothing.

That is not leniency in the decoder's sense. Recovering a malformed optional
property to its default is the schema telling this package what to do with it;
matching an arm whose schema the value does not satisfy is this package deciding
the schema said something else. The arm's alternatives are now read into the
`validate` that already enforces its `not` clause in both directions, and a
catch-all whose alternatives cannot be read that way stops generation.

## Verification

A design document is a claim about code. These are the checks that keep the two
in agreement:

- **The specification's own obligations**: the schema carries the standard's prose
  in its descriptions, and 62 of those sentences are normative. They are the part
  of the standard a generator cannot implement — not shapes but obligations — so
  each one is quoted and classified as this package's to keep or an application's,
  with where. The list is held against the schema in both directions: a release
  that adds an obligation fails rather than waiting to be noticed, and a row
  cannot outlive the clause it answers. Being classified is all it asserts; that a
  clause is satisfied is asserted by the tests each row names.
- **Cross-SDK fixtures**: 165 expected outcomes come from the reference
  TypeScript SDK's own deserialisation machinery, regenerated from the pinned
  schema and replayed by `go test` with no network. Re-running the oracle
  reproduces every previously recorded answer byte for byte, which is what makes
  the pin worth having.
- **A codec property over every generated type**: the corpus starts from JSON a
  peer sent, so it reaches the encoder only where a case re-encodes, and 163
  generated types had a `MarshalJSON` nothing called. The generator emits the list
  of types it produced and the property walks it: a zero value either encodes and
  normalises to a fixed point, or is refused by this package with a reason. The
  list is generated because the property is about all of them, and a hand-written
  one would omit exactly the type a schema bump just added. What it does not do is
  say how a populated value encodes; that is what the fixtures and the golden
  tests are for.
- **Subprocess interoperability**: five transcripts record this module's client
  against an agent built on the reference SDK as a real subprocess. One of them is
  the reference implementation eliciting from this package's client in both modes,
  which is the inbound direction an agent built on this package cannot exercise:
  its own outbound gate refuses a mode the client did not advertise.
- **Editor interoperability**: Zed spawned an agent built on this module
  and a person drove it, including the stop button. Every property Zed sent
  survives this package's types unchanged.
- **Wire fuzzing**: two targets assert that normalisation reaches a fixed point
  because schema-directed recovery can quietly break that property, and a third
  that byte-stream framing does not depend on where reads split a stream.
- **Doc links**: a test resolves every bracketed link in a doc comment, so a
  rename cannot leave documentation naming something that no longer exists.
- **Concurrency**: `testing/synctest` covers cancellation and shutdown, under
  `-race`, on Linux, macOS, and Windows.
- **Reachability**: the check reports an exported operation with no caller-side
  test or example. Repository usage alone does not decide whether a library
  export is necessary, but every retained export needs executable contract
  evidence.
- **Examples**: every package example runs under `go test`.
- **Benchmarks**: the encode, the decode and one whole turn, run for a single
  iteration in CI. They are a regression guard and not an optimisation target —
  nothing here has been tuned, and a number one of them produces is not a reason
  to tune anything. Correctness is the only dimension every other check covers, so
  a schema bump that made the per-message path several times more expensive would
  otherwise pass all of them.

## Version and release policy

The module is pre-1.0 and its Go API is expected to change; the protocol version
it targets is not. The language floor belongs to [go.mod](../go.mod) and selects
a supported, patched toolchain for the protocol validation dependencies. CI
derives both the exact floor and its Go release's latest patch from that owner.
Concurrency tests use `testing/synctest` to verify lifecycle behavior without
sleeps.

### The experimental channel is not generated, and cannot be half-opened

`schema.unstable.json` is where features are tried before they are grammar, and
where the ones that survive go to become v2: `PlanUpdate` and `PlanItems` appear
in the unstable v1 channel and again in the v2 draft. Generating from it is what
the other four Go libraries do. This one does not, and the reason is what the
channel says about itself — its contents "may be removed or changed at any point".

An exported Go type generated from a moving input is a promise this module cannot
keep. `gorelease` compares each release against the last tag, and every upstream
churn would surface as a breaking change in a module whose whole claim is that its
surface is a published grammar. The evidence that things really do leave is in this
repository's own history: `mcp/message` was in the unstable channel, this
generator carried a comment naming it, and by v1.21.0 it was gone — the comment
outlived the method.

The obvious middle course does not exist, which is worth stating because it looks
like it should. Opening the extension API to unstable method names would let a
caller send `session/fork` with types of their own — none of the 17 begins with
`_`, so today they are refused — but it would stop there. Those methods are gated
by capabilities that are named properties of `ClientCapabilities`, and this
package's generated capability types drop properties they do not know, so a caller
could send the method and never advertise it. Making capabilities retain unknown
properties would not fix it either: the reference implementation strips them too,
so the fixture corpus would start failing the moment this package kept what the
oracle discards. A half-feature whose completion requires diverging from the
oracle is not a feature.

What is reachable is what a real editor actually uses. The recorded Zed handshake
advertises its own experiments through `_meta` — `terminal_output`,
`terminal-auth` — not through unstable schema properties, and `_meta` plus
`_`-prefixed extension methods are fully supported here. An application that needs
the unstable grammar itself needs a library generated from it, and this is not one.

### The module major tracks the protocol major

Upstream is publishing `schema-v2.0.0` pre-releases, now in beta, alongside the
stable v1 line. A protocol major is a different grammar, so the question it raises is not
when to implement it but where it lives, and answering that after the work has
started is how a stopgap gets chosen.

The decision: **one package speaks one grammar, and the module major tracks the
protocol major.** When ACP 2 stabilises, this module becomes `/v2` and speaks
version 2 only. It does not learn to speak both.

The schema settles what a version number means before any of this is a judgement
call: "This version is only bumped for breaking changes. Non-breaking changes
should be introduced via capabilities." So every schema release in the v1 line —
1.19, 1.20, 1.21 — is protocol version 1, and what separates them is which
capabilities a peer advertises. There is no negotiation for this package to do
within a major that the capability gate is not already doing, and a version number
that differs is upstream saying the two grammars are incompatible.

That is worth stating beside the official MCP Go SDK, because it negotiates five
protocol versions in one package and looks at first like a counterexample. It is
not, for two reasons. Its versions are dated spec releases that mostly add, so
version is the axis along which MCP evolves and it pays for that with
`if protocolVersion >= …` branches through its client, server and transport. ACP
evolves along the capability axis instead, and reserves the version number for the
breaks. And its own policy, written down, is this one: "If feasible, the SDK will
support all versions of the MCP spec. However, if breaking changes to the spec
make this infeasible, preference will be given to the most recent version" —
with breaking API changes requiring a v2 module. ACP 2 removing eleven of
twenty-five methods is the infeasible case, named in advance.

The alternative is one module negotiating either grammar, and it fails on the
same two facts that shaped everything above. The types are generated from one
pinned schema into one package, so two grammars would be two definitions of
`PromptRequest` — either under prefixed names nobody wants to read or in
subpackages that split an API whose halves call each other. And every operation
would gain a branch on which grammar this connection settled, which is precisely
the compatibility layer this repository's rules forbid: not a path being removed,
but a second one being kept alive inside every method.

How much of a different grammar it is was measured rather than assumed.
The initial comparison of `schema-v2.0.0-alpha.3` against v1.21.0 found
40 definitions gone, 45 new, and 11 of the 25 methods removed against 2 added;
`schema-v2.0.0-beta.3` against v1.34.1 still removes the same 11 and adds 4. The
removals are not
peripheral — all five `terminal/*` methods and both `fs/*` methods stop existing,
`authenticate` and `logout` become `auth/login` and `auth/logout`, `session/load`
and `session/set_mode` go. Terminals reappear as arms of `SessionUpdate` and
running a command as a permission subject, so the client's side of the protocol is
reorganised rather than extended. A package holding both would export
`ReadTextFile` in one grammar and not the other.

The cost is real and belongs in the same paragraph as the decision. An editor
that must drive both a v1 and a v2 agent imports both modules and finds out which
it is talking to the way the protocol says — by being refused at `initialize` —
because a client cannot know an agent's grammar before the handshake it is part
of. That is two dependency lines and a fallback, against a branch inside every
operation forever. It is also exactly what Go's major-version rule exists to
express, and pre-1.0 is the cheapest moment this choice will ever be available.

Until the v2 schema stabilises, the pin stays on the v1 line and the
pre-releases are watched rather than implemented. Implementing a beta would
encode a dialect that is still changing, which is the local dialect
`PROJECT_RULES.md` rules out, arrived at by being early rather than by
disagreeing. A stable `schema-v2.0.0` release is what starts the work.

`scripts/release.sh` is the only release path. The module proxy and checksum
database make published tags immutable. The script therefore verifies before it
plans, prints the complete plan, and performs a dry run unless explicitly told to
execute it.
